# Как приложению самому записывать заказы в Google Таблицу

Исследование вариантов. Код приложения не менялся.  
Дата: 31.10.2026.

## Главный вывод

Сейчас приложение умеет только **читать** таблицу: оно скачивает публичные CSV-вкладки через `gviz` без авторизации. Для записи одного чтения мало — Google не разрешает писать в таблицу без OAuth-токена, сервисного аккаунта или промежуточного сервиса.

Для текущего проекта — один оператор, одно устройство, простая таблица — самый прагматичный вариант:

> **Google Apps Script Web App как маленький серверный посредник.**  
> Приложение отправляет HTTPS-запрос на скрипт, скрипт сам пишет в таблицу от имени владельца. В приложении не нужен Google-вход, не нужен Cloud-проект и не нужен ключ сервисного аккаунта.

Это же решение попутно позволит **закрыть таблицу от публичного чтения**: сейчас любой, у кого есть ссылка, может прочитать адреса и телефоны.

---

## Что мешает писать «просто так»

- `gviz`/CSV — только чтение.
- API-ключ Google Sheets — только чтение публичных таблиц, запись невозможна.
- Публикация таблицы в интернете, `IMPORTRANGE`, опубликованный CSV — только чтение.
- Запись требует одного из трёх: OAuth-разрешение пользователя, сервисный аккаунт или сторонний посредник.

Дополнительная сложность — **структура текущей таблицы**: ежедневные вкладки `дд.ММ.гг`, в каждой по три блока заказов (`B/C`, `I/J`, `Q/R`). Автоматическая запись прямо в эти блоки будет конфликтовать с ручным заполнением. Надёжнее писать в отдельную вкладку или отдельный диапазон, а не пытаться угадать свободную строку среди ручных записей.

## Вариант 1. Google Apps Script Web App

**Как работает**

- В таблице создаётся Apps Script, привязанный к ней.
- Публикуется как Web App: «Выполнять от имени владельца», доступ «Anyone» (анонимный).
- В скрипте есть `doPost`, который принимает JSON: номер звонка, имя, адрес, бутыли, дату, статус, локальный `recordId`.
- Скрипт проверяет секретный токен, берёт нужную вкладку, находит строку по `recordId` или добавляет новую.
- Приложение просто делает HTTPS POST и получает JSON-ответ.

**Плюсы**

- Не нужен Google-вход на телефоне.
- Не нужен Google Cloud Project, OAuth consent и проверка приложения.
- Бесплатно.
- Можно писать и читать одной точкой, а таблицу сделать приватной.
- Можно создавать вкладку на новый день, форматировать строки, проверять дубликаты.
- Простая настройка: URL + токен в настройках приложения.

**Минусы**

- URL и токен хранятся в APK/настройках — при желании их можно извлечь. Нужен длинный случайный токен и ограничение скрипта одной таблицей/вкладкой.
- Первый вызов после простоя может быть медленным (холодный старт 1–3 секунды).
- Apps Script может отдавать редирект после POST; нужна аккуратная обработка ответа и повторных попыток.
- Есть квоты Google, но для одного оператора они далеко.
- Скрипт живёт отдельно от APK: при смене Google-аккаунта или удалении скрипта запись сломается.

**Сложность:** низкая/средняя.  
**Безопасность:** приемлемая для одного устройства, но не «пуленепробиваемая».

## Вариант 2. OAuth 2.0 + Google Sheets API напрямую

**Как работает**

- Приложение запрашивает у пользователя разрешение `spreadsheets`.
- На Android это делается через `AuthorizationClient` (Google Play Services) или AppAuth.
- Дальше приложение вызывает `spreadsheets.values.append` / `values.update` напрямую.

**Плюсы**

- Официальный путь, без промежуточного скрипта.
- Токен привязан к аккаунту пользователя, его можно отозвать.
- В APK нет сервисного ключа.
- Полный контроль: обновление строк, создание вкладок, чтение и запись.
- Квоты большие: 60 операций записи в минуту на пользователя и 300 на проект.

**Минусы**

- Нужен Google Cloud Project и OAuth consent screen.
- Нужен Android OAuth client, привязанный к package name и SHA-1 подписи APK.
- Нужно хранить и обновлять токены.
- Scope `spreadsheets` — чувствительный: для публичного распространения нужна верификация Google. Для личного использования можно оставить приложение в Testing, но тогда refresh-токены живут ограниченно — обычно 7 дней, и оператору придётся периодически заново разрешать доступ.
- Пользователь может увидеть предупреждение «приложение не проверено».
- Это ломает текущий принцип «без аккаунтов и синхронизации».

**Сложность:** высокая.  
**Безопасность:** хорошая, если всё настроено правильно.

## Вариант 3. Сервисный аккаунт Google с ключом внутри приложения

**Как работает**

- Создаётся сервисный аккаунт, таблица расшаривается на его email.
- JSON-ключ кладётся в APK или импортируется на устройство.
- Приложение подписывает JWT и пишет через Sheets API без участия пользователя.

**Плюсы**

- Работает без Google-входа и без промежуточного сервера.
- Просто в реализации.
- Стабильно и быстро.

**Минусы**

- Приватный ключ в APK можно извлечь.
- Получивший ключ сможет писать в таблицу, а в зависимости от прав — читать её.
- Google прямо предупреждает, что долгоживущие ключи в клиентских приложениях — риск.
- Ротация ключа требует обновления приложения.
- Не подходит, если APK будет устанавливаться не только на ваше устройство.

**Сложность:** низкая.  
**Безопасность:** низкая. **Не рекомендую** как основной вариант.

## Вариант 4. Свой backend: Cloud Run / Cloud Functions / Firebase Functions

**Как работает**

- Приложение отправляет данные на ваш сервер.
- Сервер проверяет пользователя/устройство и пишет в таблицу через сервисный аккаунт.
- Секрет хранится только на сервере.

**Плюсы**

- Самая безопасная и гибкая схема.
- Можно вести журнал, ретраи, ограничения по устройству.
- Легко масштабируется на несколько операторов.
- Можно добавить App Check/Play Integrity.

**Минусы**

- Нужен деплой, биллинг и обслуживание.
- Для одного телефона это оверинжиниринг.
- Появляется точка отказа, которую нужно администрировать.

**Сложность:** высокая.  
**Безопасность:** высокая.

## Вариант 5. Google Forms как «канал записи»

**Как работает**

- Создаётся форма, привязанная к таблице.
- Приложение отправляет POST на `formResponse` с `entry.*` полями.
- Ответы автоматически попадают в лист.

**Плюсы**

- Очень быстро внедрить.
- Не нужен OAuth и backend.
- Данные сразу в таблице.

**Минусы**

- Только добавление, без обновления и удаления.
- Нет нормальной идемпотентности: повторный POST создаст дубль.
- `entry`-идентификаторы могут меняться при редактировании формы.
- Публичная форма может быть заспамлена.
- Ответы попадают в отдельный лист, а не в текущие ежедневные вкладки.
- Плохо подходит для адресов и телефонов с точки зрения приватности.

**Сложность:** очень низкая.  
**Безопасность:** низкая/средняя. Подходит только для чернового прототипа.

---

## Вариант 6. Сторонний webhook: Make, Zapier, n8n, SheetDB и подобные

**Как работает**

- Приложение отправляет запрос на webhook стороннего сервиса.
- Сервис пишет в таблицу.

**Плюсы**

- Быстро.
- Не нужно писать Google-авторизацию.
- У n8n может быть self-hosted.

**Минусы**

- Данные проходят через третью сторону.
- Платно или с лимитами.
- Зависимость от чужого сервиса.
- Латентность и точки отказа.
- Для персональных данных клиентов — сомнительно.

**Сложность:** низкая.  
**Безопасность:** зависит от выбранного сервиса.

## Рекомендуемая схема для этого приложения

1. **Отдельная вкладка `Приложение`** в той же таблице. Не писать в ежедневные блоки `B/C`, `I/J`, `Q/R` — там ручной формат.
2. Колонки: `recordId`, `дата`, `время`, `телефон`, `имя`, `адрес`, `бутыли`, `принят/пропущен`, `день доставки`, `статус`, `обновлено`.
3. Приложение отправляет `recordId` + ревизию записи. Скрипт ищет строку по `recordId`: если есть — обновляет, если нет — добавляет. Это защищает от дублей при ретраях.
4. Запись запускается **при сохранении формы** и повторно при закрытии заказа. Если нужен только окончательный заказ — при «Заказы обработаны».
5. На устройстве добавляется очередь синхронизации: `syncStatus`, `lastError`, `syncedRevision`. Отправка идёт через WorkManager с повтором при появлении сети. Интерфейс не должен ждать Google.
6. В Apps Script — `LockService`, чтобы два запроса не писали одновременно.
7. Токен — длинный случайный, хранится в настройках; скрипт принимает только его и только одну таблицу. Токен можно менять без обновления APK.

---

## Что важно решить до реализации

- Писать каждую карточку или только закрытые заказы?
- Нужно ли обновлять строку при исправлении заказа?
- Писать ли пропущенные звонки и «не клиентов»?
- Писать в текущие ежедневные вкладки или в отдельную?
- Что делать, если оператор вручную изменил строку в таблице?
- Нужен ли обратный статус из таблицы в приложение (двусторонняя синхронизация)?
- Готовы ли вы держать Apps Script и токен, или нужен полностью «белый» OAuth-путь?
